# Архитектура MeteoCare

В проекте используется сочетание **Clean Architecture** и **MVVM**. Приложение разделено на Data, Domain и Presentation слои. Для управления зависимостями используется Koin.

## 1. Структура приложения

Основные функциональные области проекта:

- **forecast** — получение и отображение погодных данных через Open-Meteo API;
- **geoLocation** — определение местоположения пользователя;
- **profile** — авторизация и хранение пользовательского профиля через Firebase;
- **ai** — анализ погодных условий и генерация рекомендаций с помощью Gemini API;
- **dailyAdvice** — формирование и сохранение ежедневных рекомендаций;
- **pushMessages** — планирование и отображение системных уведомлений;
- **ui** — экраны приложения и навигация;
- **di** — конфигурация внедрения зависимостей.

## 2. Data Layer

Data Layer отвечает за взаимодействие с внешними сервисами и системными компонентами Android.

**Погодные данные**

`MeteoApiService` описывает запросы к Open-Meteo API, а Retrofit выполняет сетевые обращения. Репозиторий получает и преобразует данные о температуре, влажности, давлении, ветре и осадках.

**Геолокация**

Для определения координат пользователя используется Google Play Services Location. Полученные координаты применяются при запросе прогноза погоды.

**Профиль пользователя**

Для авторизации используется Firebase Authentication, а для хранения пользовательских данных и ежедневных статусов — Cloud Firestore.

**AI-анализ**

Для генерации рекомендаций используется Gemini API. Основные компоненты:

- `GeminiRetrofitService` — выполнение запросов к Gemini API;
- `AiRepositoryImpl` — взаимодействие с AI-сервисом;
- `WeatherFeatureExtractor` — извлечение погодных характеристик;
- `AdvicePromptBuilder` и `StatusPromptBuilder` — формирование запросов;
- `AiResponseMapper` — обработка ответов AI.

**Уведомления**

`DailyNotificationWorker` выполняет периодические фоновые задачи через WorkManager. `NotificationHelper` отвечает за создание канала и отображение уведомлений. Настройки сохраняются через SharedPreferences.

## 3. Domain Layer

Domain Layer содержит бизнес-логику приложения и не зависит от конкретных способов получения данных или отображения интерфейса.

В слое используются:

- доменные модели;
- интерфейсы репозиториев;
- интеракторы (Interactors);
- сценарии использования (Use Cases).

Основные сценарии:

- получение прогноза погоды;
- определение местоположения пользователя;
- работа с профилем;
- анализ погодных условий;
- формирование персональных рекомендаций;
- сохранение ежедневного статуса;
- планирование уведомлений.

## 4. Presentation Layer

Presentation Layer отвечает за отображение данных и обработку пользовательских действий.

Основные компоненты:

- `MainActivity` — точка входа в приложение;
- Jetpack Compose — построение интерфейса;
- `MeteoNavGraph` — организация навигации;
- ViewModel — обработка действий пользователя;
- StateFlow — передача состояния от ViewModel к UI.

Основные экраны приложения — прогноз погоды и профиль пользователя. Для оформления используется Material 3, для навигации — Navigation Compose, для отображения графиков — Vico.

## 5. Внедрение зависимостей

Для Dependency Injection используется Koin.

Конфигурация зависимостей разделена по функциональным областям: `WeatherForecastModule`, `LocationModule`, `ProfileModule`, `AiModule`, `DailyAdviceModule` и `NotificationModule`.

Такой подход позволяет централизованно управлять созданием репозиториев, сетевых компонентов и интеракторов.

## 6. Использованные архитектурные подходы и паттерны

**Repository Pattern**

Репозитории скрывают детали получения и хранения данных от остальных слоёв приложения.

**Dependency Injection**

Koin используется для предоставления зависимостей и управления их созданием.

**Observer Pattern**

StateFlow позволяет наблюдать за изменениями состояния и обновлять интерфейс при поступлении новых данных.

**MVVM**

ViewModel отделяет логику представления от пользовательского интерфейса и управляет состоянием экранов.

## 7. Основные сценарии работы

**Получение прогноза погоды**

1. Приложение определяет координаты пользователя.
2. Координаты передаются в сценарий получения погодных данных.
3. Репозиторий выполняет запрос к Open-Meteo API через Retrofit.
4. Полученные данные преобразуются в модели приложения.
5. ViewModel обновляет состояние интерфейса.

**Формирование рекомендаций**

1. Приложение получает погодные данные и информацию из профиля.
2. `WeatherFeatureExtractor` подготавливает характеристики для анализа.
3. Prompt Builder формирует запрос для Gemini API.
4. AI возвращает рекомендации и оценку состояния.
5. `AiResponseMapper` обрабатывает ответ.
6. Результат сохраняется в профиле пользователя через Firestore.

**Отправка уведомлений**

1. Приложение планирует периодическую задачу через WorkManager.
2. По расписанию запускается `DailyNotificationWorker`.
3. Проверяются настройки уведомлений.
4. `NotificationHelper` формирует и отображает системное уведомление.

## 8. Текущие ограничения реализации

В текущей версии AI-анализ выполняется через облачный Gemini API, поэтому для генерации рекомендаций требуется подключение к интернету.

Пока не реализованы:

- локальный запуск языковой модели на устройстве;
- дообучение собственной модели на подготовленных данных;
- расширенная история погодных показателей и рекомендаций.

Эти задачи включены в [планы дальнейшего развития](docs/roadmap.md).
